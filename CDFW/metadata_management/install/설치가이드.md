# 메타데이터 관리 프레임워크 — 설치 가이드

> 기술해설서 2.2.15 절을 "아무것도 깔려 있지 않은 Ubuntu 서버에 처음부터 설치한다"는
> 관점으로 다시 정리한 문서입니다. 설치 순서대로 한 컴포넌트씩 진행하며,
> 각 컴포넌트의 설정값은 소스에 하드코딩하지 않고 `.env`(환경변수)로 빼서 주입합니다.

## 대상 소스

- GitHub: `etri/FeDiT` → `CDFW/metadata_management/`
  - `keti_dt_platform_admin_ms` — Platform Admin API
  - `keti_dt_metadata_api` — Metadata API
  - `keti_dt_metadata_web` — Metadata Web (Vue 3)
  - `keti_dt_security_module` — 인증 서버
  - ~~`keti_dt_metadata_vector`~~ — 본 가이드 범위에서 제외

## 구성 방침

- **PostgreSQL**: 서버에 직접(패키지) 설치
- **그 외 전부 Docker**: Virtuoso · Neo4j · Elasticsearch/Kibana · InfluxDB2 · 인증서버 · Admin API · Metadata API · Web
- 모든 컨테이너는 공용 도커 네트워크 **`keti-dt-net`** 위에서 **컨테이너명**으로 서로 통신
- PostgreSQL만 컨테이너 밖(호스트)에 있으므로, 컨테이너에서는 **도커 게이트웨이 IP**로 접속

## 서버 사양

| 구분 | 최소 | 권장 |
|---|---|---|
| CPU | 4 core | 8 core |
| RAM | 16 GB | 32 GB |
| 디스크 | 200 GB SSD | 500 GB 이상 (데이터 볼륨 분리) |

한 서버에 저장소 5종(PostgreSQL·Virtuoso·Neo4j·Elasticsearch·InfluxDB)과 앱 4종이 함께 뜬다.
메모리를 많이 쓰는 순서는 **Elasticsearch → Neo4j → Virtuoso → Java API** 이며,
각 컴포넌트가 기본값으로는 호스트 메모리의 일정 비율을 잡으려 하므로 **힙을 명시적으로 제한**한다.

```
Elasticsearch   ES_JAVA_OPTS=-Xms4g -Xmx4g        # RAM 의 1/4 수준, 31g 초과 금지
Neo4j           server.memory.heap.max_size=2g
                server.memory.pagecache.size=2g
Java API 2종    JAVA_OPTS=-Xmx1g
```

운영에서 실제로 문제가 되는 쪽은 메모리보다 **디스크**다. 데이터가 계속 쌓이기 때문에
설치 시점에 아래 두 가지를 정해두는 것이 좋다.

| 대상 | 조치 |
|---|---|
| 컨테이너 로그 (기본 무제한) | `docker run` 에 `--log-opt max-size=100m --log-opt max-file=3` |
| InfluxDB 시계열 | `.env.influxdb2` 에 `DOCKER_INFLUXDB_INIT_RETENTION=365d` 등 보존 기간 지정 |
| Elasticsearch 색인 | 문서 수에 비례해 증가. 주기적으로 `_cat/indices?v` 로 용량 확인 |

> 검증에 사용한 환경은 CPU 4 / RAM 7.8GB / Disk 58GB(Multipass VM)이며,
> 전 컴포넌트를 띄우는 것까지는 가능하지만 운영용으로는 부족하다.

## 설정값 관리 방침

설치에 쓰는 값(서버 주소·계정·비밀번호)은 **`~/dt.env` 파일 한 곳**에 모아두고
`source ~/dt.env` 로 불러 쓴다. 이후 모든 명령과 앱 실행이 이 값을 참조한다.

앱(Java) 설정은 `application-env.yml` 의 **`dev` 프로필**을 쓰며, 값이 `${변수:기본값}`
형태라 **환경변수를 주지 않으면 이 문서의 기본값 그대로 동작**한다. 바꾼 값만
컨테이너 실행 시 `-e` 로 넘기면 된다.

| 구분 | 값 |
|---|---|
| 컨테이너끼리 통신 | 컨테이너명 사용 (`virtuoso`, `neo4j`, `elasticsearch`, `influxdb2`, `keti-dt-security`, `keti-dt-platformadmin-api`) |
| 컨테이너 → 호스트 PostgreSQL | 도커 게이트웨이 `172.25.0.1` |
| 브라우저가 여는 주소 | 실제 서버 IP 또는 도메인 (`SERVER_HOST`, `WEB_SERVER_URL`) |

## 1. 사전 준비 (Docker)

### 1.1 대상 OS
- Ubuntu 20.04 LTS 이상

### 1.2 기존 Docker 제거 (구버전이 있을 경우만)
```bash
sudo apt-get remove -y docker docker-engine docker.io containerd runc
```

### 1.3 필수 패키지 설치
```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg lsb-release
```

### 1.4 Docker 공식 GPG 키 등록
```bash
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
```

### 1.5 Docker 저장소 등록
```bash
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
```

### 1.6 Docker Engine + Compose 플러그인 설치
```bash
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
```

### 1.7 설치 확인
```bash
sudo docker --version          # 예) Docker version 24.x
sudo docker compose version    # 예) Docker Compose version v2.x
sudo docker run --rm hello-world
```

> 본 가이드는 Docker Compose v2(`docker compose`, 띄어쓰기) 기준입니다.
> 구버전 `docker-compose`(붙임표)만 있는 서버라면 명령의 `docker compose`를 `docker-compose`로 바꿔 읽으면 됩니다.

### 1.8 sudo 없이 docker 사용 (선택)
```bash
sudo usermod -aG docker $USER
# 로그아웃 후 재접속하면 적용됨
```

### 1.9 ★ 공용 도커 네트워크 생성 (필수)
> 모든 컨테이너는 `keti-dt-net` 네트워크에서 **컨테이너명으로 서로를 찾습니다.**
> 이 네트워크를 먼저 만들어야 이후 모든 단계가 동작합니다.
```bash
sudo docker network create keti-dt-net
sudo docker network ls | grep keti-dt-net   # 생성 확인
```

### 1.10 도커 컴포넌트 공통 — 기준 디렉터리
> 각 컨테이너의 데이터/설정 볼륨을 한 곳에 모은다. 서버마다 계정이 다르므로
> 아래 `DT_DIR` 하나만 정하면 이후 명령을 그대로 복사해 쓸 수 있다.
```bash
export DT_DIR=$HOME/dtmeta      # 예) /root/dtmeta 또는 /home/사용자/dtmeta
mkdir -p $DT_DIR
echo $DT_DIR
```
> 재접속 시 매번 `export` 하거나, `~/.bashrc`에 넣어두면 편하다.

## 2. PostgreSQL + PostGIS (호스트 직접 설치)

### 2.1 설치 (PostgreSQL 16)
> Ubuntu 22.04 기본 저장소에는 14만 있고, 14는 2026년 11월에 지원이 끝난다.
> 지원 기간이 남은 **16**을 PostgreSQL 공식 저장소(PGDG)에서 설치한다.
```bash
# 공식 저장소 등록
sudo apt-get install -y curl ca-certificates gnupg lsb-release
sudo install -d /usr/share/postgresql-common/pgdg
curl -fsSL https://www.postgresql.org/media/keys/ACCC4CF8.asc | \
  sudo tee /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc
echo "deb [signed-by=/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc] https://apt.postgresql.org/pub/repos/apt $(lsb_release -cs)-pgdg main" | \
  sudo tee /etc/apt/sources.list.d/pgdg.list

# 설치
sudo apt-get update
sudo apt-get install -y postgresql-16 postgresql-contrib postgresql-16-postgis-3
psql --version     # 16.x 확인
```
> 다른 메이저 버전을 쓸 경우 `postgresql-<버전>`, `postgresql-<버전>-postgis-3` 으로 패키지명을 맞춘다.

### 2.2 컨테이너에서 접속 가능하도록 설정 (중요)
> 도커 컨테이너(API 등)는 호스트의 PostgreSQL에 **도커 게이트웨이 IP**로 접속한다.
> 기본은 localhost만 열려 있으므로 외부 접속을 허용해야 한다.
```bash
# 리슨 주소 개방
sudo sed -i "s/^#\?listen_addresses.*/listen_addresses = '*'/" \
  /etc/postgresql/*/main/postgresql.conf

# 도커 네트워크 대역에서의 접속 허용 (pg_hba.conf 맨 아래에 추가)
echo "host    all    all    172.16.0.0/12    md5" | \
  sudo tee -a /etc/postgresql/*/main/pg_hba.conf

sudo systemctl restart postgresql
```
> `172.16.0.0/12`는 도커 기본 대역(172.17~172.31)을 포함한다. 게이트웨이 IP는
> `docker network inspect bridge`로 확인 가능(보통 172.17.0.1 또는 172.26.0.1).

### 2.3 DATABASE / USER 생성 (DB 2개)
> 이 시스템은 **DB를 2개** 쓴다.
> - `dtmeta` — 메타데이터(Admin/Metadata API용), 유저 `meta_manager`
> - `hubsecurity` — **인증 서버 전용**, 유저 `hubsecurity_manager` (원래 기술해설서엔 누락)
```bash
sudo -u postgres psql
```
```sql
-- 1) 메타데이터 DB (Admin/Metadata API 공용 — 필요하면 API별로 DB/USER를 분리해도 됨)
create database dtmeta encoding 'utf-8';
create user meta_manager password 'rhksflwk1!';
alter user meta_manager createdb;
alter database dtmeta owner to meta_manager;

-- dtmeta DB에 스키마 2개 생성 (기술해설서 원본 절차)
\c dtmeta
create schema dtmeta authorization meta_manager;
create schema common authorization meta_manager;

-- dtmeta 스키마에 PostGIS 확장
create extension postgis with schema dtmeta;

-- 2) 인증 서버 DB
\c postgres
create database hubsecurity encoding 'utf-8';
create user hubsecurity_manager password 'rhksflwk1!';
alter database hubsecurity owner to hubsecurity_manager;

\q
```
> 비밀번호(`rhksflwk1!`)는 이후 **앱 설정과 반드시 일치**해야 한다.
> (환경변수화 단계에서 `.env`의 `DB_PASSWORD` / `HUBSECURITY_DB_PASSWORD` 로 관리)
> ERD에서 새로 뽑는 DDL에 `CREATE SCHEMA` 가 포함돼 있으면, 위 수동 스키마 생성과 중복되지 않게 한쪽만 둔다.

### 2.4 DDL / DML 실행
> DBeaver 등으로 접속해서 각 DB에 스키마(DDL)·데이터(DML)를 넣는다.

**① 메타데이터 DB (`dtmeta`)** — 접속 `jdbc:postgresql://{Server IP}:5432/dtmeta` / `meta_manager`
- DDL: 스키마 `common`, `dtmeta` + `tb_com_*` 등 테이블 → **ERD에서 새로 생성** (진행 중)
- DML: 코드/메뉴/단위/검증 등 기준 데이터
- 참고본: `설치문서/20260402_cotlab설치/psql_ddl_dml_dev/dtmeta_schema.sql`, `dtmeta_data.sql`

**② 인증 DB (`hubsecurity`)** — 접속 `.../hubsecurity` / `hubsecurity_manager`
- DDL: `public.users` / `role` / `application` / `token` / `session` / `keystore` / `authcode` / `vericode` / `user_app_map`
- DML: 초기 계정·권한·앱 등록 데이터
- 참고본: `설치문서/20260402_cotlab설치/psql_ddl_dml_dev/hubsecurity_schema.sql`, `hubsecurity_data.sql`

## 3. Virtuoso (Docker)

### 3.1 실행
```bash
docker run \
  --name virtuoso \
  --publish=1111:1111 \
  --publish=8890:8890 \
  --volume=$DT_DIR/virtuoso/database:/database \
  --detach \
  -e DBA_PASSWORD=rhksflwk1! \
  --network keti-dt-net \
  openlink/virtuoso-opensource-7:7.2.6-r10-g5a27710
```
> 내부 개발계와 동일 버전(`7.2.6-r10-g5a27710`)으로 고정.

### 3.2 Conductor 접속 및 계정 생성
- 접속: `http://{Server IP}:8890/conductor`
- `dba` 로그인 → **System Admin – User Accounts** 에서 `meta_manager` 계정 생성
  - User Type: `SQL/ODBC`, Primary Role: `dba`
  - Account Roles: `SPARQL_LOAD_SERVICE_DATA`, `SPARQL_SELECT`, `SPARQL_SPONGE`, `SPARQL_UPDATE`
  - Default Permissions: 전부 체크 → save
- `meta_manager`로 재로그인 → **Linked Data – SPARQL** 에서 동작 확인
  - `select * where { ?s ?p ?o }`

## 4. Neo4j (Docker)

### 4.1 플러그인 jar 배치 (apoc, n10s)
> `NEO4J_PLUGINS='["apoc"]'` 는 apoc만 자동설치하므로, RDF 엔드포인트에 쓰는
> **n10s(neosemantics)** 는 jar를 직접 플러그인 볼륨에 넣는다.
```bash
mkdir -p $DT_DIR/neo4j/plugins
# 참고본: 설치문서/20260402_cotlab설치/neo4j_plugins/{apoc.jar, n10s.jar}
cp apoc.jar n10s.jar $DT_DIR/neo4j/plugins/
```

### 4.2 실행
```bash
docker run \
  --name neo4j \
  --publish=7474:7474 \
  --publish=7687:7687 \
  --volume=$DT_DIR/neo4j/data:/data \
  --volume=$DT_DIR/neo4j/conf:/conf \
  --volume=$DT_DIR/neo4j/plugins:/plugins \
  --env NEO4J_PLUGINS='["apoc"]' \
  --env NEO4J_AUTH=neo4j/rhksflwk1! \
  --env DBMS_SECURITY_AUTH_ENABLED=true \
  --env DBMS_UNMANAGED_EXTENSION_CLASSES=n10s.endpoint=/rdf \
  --network keti-dt-net \
  --detach \
  neo4j:2026.03.1
```
> cotlab 실제 설치 버전 **2026.03.1** 로 고정 (Neo4j 달력형 버전).
> `latest`는 재현이 안 되므로 정확한 태그로 박아둔다.
> 옛 문서의 `NEO4JLABS_PLUGINS`는 **`NEO4J_PLUGINS`**(신버전 표기)로 변경됨.
> RDF 엔드포인트(`n10s.endpoint=/rdf`)를 실제로 쓰려면 neosemantics(n10s) 플러그인 jar가
> `/plugins`에 있어야 한다. (현재 apoc만 자동설치)

### 4.3 Browser 접속 및 초기 설정
- 접속: `http://{Server IP}:7474/browser` → `neo4j / rhksflwk1!` 로그인
- 초기 제약조건 설정 (중복 방지):
```cypher
CREATE CONSTRAINT IF NOT EXISTS FOR (r:Resource)     REQUIRE r.uri       IS UNIQUE;
CREATE CONSTRAINT IF NOT EXISTS FOR (m:MetaResource) REQUIRE m.metaSetId IS UNIQUE;
```
> 실제 라벨/속성명은 소스 기준으로 확인 후 반영. (문서 원문: Resource.uri, metadataResource.medataSetId)

### 5.2 `.env` 수정
```ini

KIBANA_SYSTEM_PASSWORD=rhksflwk1!
```

### 5.3 `docker-compose.yml` — keti-dt-net 연결
각 서비스(elasticsearch/kibana/logstash 등)에 네트워크를 추가하고, 파일 하단에 external 선언:
```yaml
    networks:
      - keti-dt-net

networks:
  keti-dt-net:
```

## 앱 배포 공통 사항

- **실행 순서(중요):** `인증서버 → Platform Admin API → Metadata API → Web` 순으로 기동해야 로그인이 된다.
- 대상 소스: `etri/FeDiT` → `CDFW/metadata_management/`의 각 폴더. 폴더로 이동 후 빌드.
- 빌드/런에 쓰는 파일은 그동안 환경별 변형(`DockerfileCotlab`, `server_conf_cotlab.json`, `default_cotlab.conf`, `npm run build_cotlab`)을 **복제해 값만 바꾸는** 방식이었다 → **환경변수화(.env)로 통합 예정.**
- **프로필:** 새 설치에서는 Java 앱 프로필을 **`dev`** 로 통일한다 (`-e SPRING_PROFILES_ACTIVE=dev`).
  기존 cotlab 설정은 파일명(`application-cotlab.yml`)과 내부 활성 프로필(`on-profile: cotlab_dev`)이 어긋나 있었으므로 그대로 쓰지 않는다.
  `dev` 프로필이 참조할 설정값은 환경변수화 단계에서 `.env`로 정리한다.

## 7. 인증 서버 (keti-dt-security, Node.js)

> ★ 기존 기술해설서에 **누락**되어 있던 컴포넌트. 웹 로그인의 전제이므로 가장 먼저 기동.
> **스마트시티 인증서버 기반**으로 커스터마이즈한 `keti_dt_security_module`(우리 copy)를 사용한다.
> 상류를 새로 내려받지 않는다 — 우리 `hubsecurity` 스키마·OAuth 설정에 맞춰져 있어 그대로 써야 다른 컴포넌트와 붙는다.
> Node.js/Express 앱이며 설정은 `server_conf.json`, 인증키는 `keys/private.pem`·`public.pem` 사용.
> **PostgreSQL의 `hubsecurity` DB**(섹션 2에서 생성)에 접속한다.

### 7.1 설정 파일 준비 (`server_conf.json`)
> DockerfileCotlab이 `COPY server_conf_cotlab.json server_conf.json` 으로 설정을 이미지에 굽는다.
> 새 서버에 맞춰 `server_conf_cotlab.json`(또는 새 환경용 복제본)의 값을 수정한다.
```jsonc
{
  "serverip":   "{Server IP}",       // 이 인증서버가 뜨는 서버 IP
  "serverport": 33000,
  "dbUserId":   "hubsecurity_manager",
  "dbUserPwd":  "rhksflwk1!",
  "dbHost":     "172.25.0.1",         // keti-dt-net 게이트웨이 (docker network inspect keti-dt-net 로 확인)
  "dbName":     "hubsecurity",
  "dbPort":     5432,
  "token_type": "JWS",
  "program_type": "general",
  "default_url": "{Server IP}:33000"
}
```
> `dbHost`는 컨테이너에서 **호스트 PostgreSQL**로 나가는 게이트웨이 IP다. 서버마다 다르므로
> `docker network inspect keti-dt-net --format '{{(index .IPAM.Config 0).Gateway}}'` 로 확인해 넣는다.
> → 이 하드코딩 값들(IP·비번·게이트웨이)이 **환경변수화 대상**이다.

### 7.2 사전 확인
- `keys/private.pem`, `keys/public.pem` 존재 (JWT/OAuth 서명키)
- `hubsecurity` DB에 DDL/DML 반영 완료
  - DDL: `ddl_hubsecurity_public.sql`
  - DML: `dml_hubsecurity_public_data.sql`
  - ★ **필수 seed**: `System_Admin` 롤 + `admin` 계정 + `security` 앱 — 이 3건이 없으면 **로그인/OAuth 토큰 발급이 안 된다.**

### 7.3 빌드
```bash
cd keti_dt_security_module
docker build --no-cache -t keti-dt-security-image:latest -f DockerfileCotlab .
```

### 7.4 실행
```bash
docker run -dp 33000:33000 \
  --name keti-dt-security \
  --network keti-dt-net \
  --restart unless-stopped \
  keti-dt-security-image:latest
```
