# 메타데이터 관리 프레임워크 — 설치 가이드

> 기술해설서 2.2.15 절을 "아무것도 깔려 있지 않은 Ubuntu 서버에 처음부터 설치한다"는
> 관점으로 다시 정리한 문서입니다. 설치 순서대로 한 컴포넌트씩 진행하며,
> 각 컴포넌트의 설정값은 소스에 하드코딩하지 않고 `.env`(환경변수)로 빼서 주입합니다.

## 대상 소스

- GitHub: `etri/FeDiT` → `CDFW/metadata_management/`
  - `keti_dt_platform_admin_ms` — Platform Admin API
  - `keti_dt_metadata_api` — Metadata API
  - `keti_dt_metadata_web` — Metadata Web (Vue 3)
  - `keti_dt_security_module` — 인증 서버
  - `keti_dt_metadata_vector` — 벡터 검색 서버(선택). 벡터 검색 기능을 쓸 때 추가로 설치하며,
    설치하지 않아도 나머지 기능은 정상 동작한다. 본 문서에서는 다루지 않는다.

## 구성 방침

- **PostgreSQL**: 서버에 직접(패키지) 설치
- **그 외 전부 Docker**: Virtuoso · Neo4j · Elasticsearch/Kibana · InfluxDB2 · 인증서버 · Admin API · Metadata API · Web
- 모든 컨테이너는 공용 도커 네트워크 **`keti-dt-net`** 위에서 **컨테이너명**으로 서로 통신
- PostgreSQL만 컨테이너 밖(호스트)에 있으므로, 컨테이너에서는 **도커 게이트웨이 IP**로 접속

## 서버 사양

| 구분 | 최소 | 권장 |
|---|---|---|
| CPU | 4 core | 8 core |
| RAM | 16 GB | 32 GB |
| 디스크 | 200 GB SSD | 500 GB 이상 (데이터 볼륨 분리) |

한 서버에 저장소 5종(PostgreSQL·Virtuoso·Neo4j·Elasticsearch·InfluxDB)과 앱 4종이 함께 뜬다.
메모리를 많이 쓰는 순서는 **Elasticsearch → Neo4j → Virtuoso → Java API** 이며,
각 컴포넌트가 기본값으로는 호스트 메모리의 일정 비율을 잡으려 하므로 **힙을 명시적으로 제한**한다.

```
Elasticsearch   ES_JAVA_OPTS=-Xms4g -Xmx4g        # RAM 의 1/4 수준, 31g 초과 금지
Neo4j           server.memory.heap.max_size=2g
                server.memory.pagecache.size=2g
Java API 2종    JAVA_OPTS=-Xmx1g
```

운영에서 실제로 문제가 되는 쪽은 메모리보다 **디스크**다. 데이터가 계속 쌓이기 때문에
설치 시점에 아래 두 가지를 정해두는 것이 좋다.

| 대상 | 조치 |
|---|---|
| 컨테이너 로그 (기본 무제한) | `docker run` 에 `--log-opt max-size=100m --log-opt max-file=3` |
| InfluxDB 시계열 | `.env.influxdb2` 에 `DOCKER_INFLUXDB_INIT_RETENTION=365d` 등 보존 기간 지정 |
| Elasticsearch 색인 | 문서 수에 비례해 증가. 주기적으로 `_cat/indices?v` 로 용량 확인 |

> RAM 8GB 에서도 전 컴포넌트가 기동되기는 하지만, 여유가 없어 운영에는 권장하지 않는다.

## 설정값 관리 방침

설치에 쓰는 값(기준 디렉터리·서버 주소·계정·비밀번호)은 **`~/dt.env` 파일 한 곳**에
모아두고 `source ~/dt.env` 로 불러 쓴다. 이후 모든 명령과 앱 실행이 이 값을 참조한다.
비밀번호가 들어 있으므로 `chmod 600` 으로 권한을 제한한다.

앱(Java) 설정은 `application-env.yml` 의 **`dev` 프로필**을 쓰며, 값이 `${변수:기본값}`
형태라 **환경변수를 주지 않으면 이 문서의 기본값 그대로 동작**한다. 바꾼 값만
컨테이너 실행 시 `-e` 로 넘기면 된다.

| 구분 | 값 |
|---|---|
| 컨테이너끼리 통신 | 컨테이너명 사용 (`virtuoso`, `neo4j`, `elasticsearch`, `influxdb2`, `keti-dt-security`, `keti-dt-platformadmin-api`) |
| 컨테이너 → 호스트 PostgreSQL | 도커 게이트웨이 `172.25.0.1` |
| 브라우저가 여는 주소 | 실제 서버 IP 또는 도메인 (`SERVER_HOST`, `WEB_SERVER_URL`) |

### OAuth 클라이언트

인증에 쓰는 클라이언트가 **두 개**이고 용도가 다르다. 서로 바꿔 쓰면 로그인이 안 된다.

| 앱 이름 | client_id | redirect_uri | 쓰는 곳 |
|---|---|---|---|
| `security` | `3eRofhrl6wPWauX2u0GT` | 인증 서버 주소 (`http://서버IP:33000`) | 인증 서버 로그인 화면 |
| `metaweb` | `uFbj72aY5iJ266bI3T2O` | 웹 주소 + `/redirect` | 메타데이터 웹 |

`security` 는 인증 서버가 자기 로그인 화면에서 토큰을 받을 때 쓴다. 이 행이 없으면
로그인 화면은 뜨지만 제출할 때 401 이 나고 **브라우저가 아이디/비밀번호 팝업**을 띄운다.

`metaweb` 은 웹이 인증 서버로 넘어갔다 돌아올 때 쓴다. **웹 빌드 시 넘기는
`CLIENT_ID`/`CLIENT_SECRET` 과 DB 값이 같아야 하고, `redirect_uri` 도 웹의
`VUE_APP_N2M_REDIRECT_URI` 와 글자까지 같아야 한다.** 인증 서버가
protocol/host/port/path 를 정확히 비교하므로 포트 하나만 달라도 실패한다.

DML 의 치환자 두 개가 이 값들이다.

| 치환자 | 값 |
|---|---|
| `__WEB_SERVER_URL__` | `$WEB_SERVER_URL` (웹 주소, 끝에 `/` 없음) |
| `__SECURITY_SERVER_URL__` | `http://$SERVER_HOST:33000` |

### 초기 계정

DML 로 8개 계정이 만들어지며 **비밀번호는 모두 `rhksflwk1!`** 이다.
운영 서버에서는 반드시 변경한다.

| 계정 | 권한 |
|---|---|
| `meta_admin` | 시스템 관리자 (설치 확인은 이 계정으로 한다) |
| `keti_dt`, `admin`, `n2m_iot` | 시스템 관리자 |
| `meta_tester1` ~ `meta_tester4` | 제공자 / 관리자 / 조회자 / 기본 사용자 |

로그인 자체는 `hubsecurity` DB 의 `users` 가, 화면에 보이는 메뉴는 `dtmeta` DB 의
`common.tb_com_authusermap` 이 결정한다. 둘 다 있어야 정상 동작한다.

### https 를 쓰지 않는다

이 설치는 전 구간 http 다. 브라우저가 https 로 바꿔 접속하면 인증서 경고가 뜨고
로그인 화면에 갈 수 없다. 주소창에 `http://` 를 직접 붙여 입력하고, 크롬 설정의
**"항상 보안 연결 사용"** 을 끈다.

# 설치 절차

**실제 명령은 `설치스크립트.txt` 에 있습니다.** 스크립트를 위에서부터 순서대로
복사해 실행하고, 이 문서는 각 단계가 무엇을 하는지와 막혔을 때 볼 곳을 설명합니다.

스크립트의 블록 번호(`1-2`, `2-5` 같은)와 아래 절 번호가 대응합니다.

## 0. 설치 전 확인과 값 지정

**하는 일** — OS·사양·기존 설치 여부·포트 점유를 확인하고, 설치 전체에서 쓸 값을
`~/dt.env` 파일에 모아 둔 뒤, 그 값이 가리키는 위치로 소스를 받습니다.

**`~/dt.env` 가 이 설치의 기준점입니다.** 서버 주소·계정·비밀번호를 여기 한 번만
적어 두면 이후 모든 단계가 이 값을 참조합니다. 값 지정(0-2)이 소스 받기(0-3)보다
먼저인 이유는, 소스를 내려받을 위치(`DT_DIR`)와 내려받은 소스의 경로(`SRC_DIR`)를
여기서 정하기 때문입니다.

`~/.bashrc` 에 `source ~/dt.env` 를 등록하므로 재접속하면 값이 자동으로 살아납니다.
등록 전 세션이나 다른 셸에서는 `source ~/dt.env` 를 직접 실행합니다.

| 확인할 것 | 정상 |
|---|---|
| `SERVER_HOST` | 브라우저가 실제로 접속할 주소. 서버 내부 IP가 아님 |
| `172.25` 대역 | 이미 쓰이고 있지 않아야 함 (도커 네트워크와 충돌) |
| 포트 | 5432·8890·7474·9200·5601·8086·33000·6998·16997·8084 비어 있어야 함 |

> **클라우드 서버**라면 서버 안 방화벽과 별개로 인스턴스 바깥의 보안그룹이 있습니다.
> 브라우저가 직접 호출하는 **8084·33000·6998·16997** 은 반드시 열려야 로그인이 됩니다.
> 관리 콘솔(7474·8890·5601·8086)과 DB(5432)는 관리자 IP만 열거나 SSH 터널로 대신합니다.

## 1. Docker

**하는 일** — Docker Engine과 공용 네트워크 `keti-dt-net` 을 준비합니다.

**기존 도커는 건드리지 않습니다.** 이미 설치된 서버라면 그대로 두고, `docker compose`
만 안 되는 경우에 플러그인을 얹습니다. 남의 컨테이너와 볼륨을 지우지 않기 위해서입니다.

**네트워크 대역을 `172.25.0.0/16` 으로 고정합니다.** 그래야 게이트웨이가 항상
`172.25.0.1` 이 되고, 컨테이너에서 호스트 PostgreSQL로 접속하는 주소를 서버마다
바꾸지 않아도 됩니다.

| 막히는 곳 | 대처 |
|---|---|
| 서비스 재시작 확인 창에서 멈춤 | 스크립트가 `NEEDRESTART_MODE=a` 로 넘깁니다 |
| `docker ps` 권한 오류 | `newgrp docker` 로 그룹을 현재 셸에 적용 |
| `172.25` 대역 충돌 | 다른 대역으로 바꾸고, 이후 `172.25.0.1` 이 나오는 곳도 함께 수정 |

## 2. PostgreSQL

**하는 일** — PostgreSQL 16 + PostGIS를 호스트에 직접 설치하고, DB 2개와 계정을
만든 뒤 SQL 6종을 넣습니다.

**PostgreSQL만 컨테이너 밖에 둡니다.** 데이터 안정성과 백업·운영 편의 때문이며,
그래서 컨테이너에서는 도커 게이트웨이(`172.25.0.1`)로 접속합니다.

**16을 쓰는 이유** — Ubuntu 22.04 기본은 14인데 2026년 11월에 지원이 끝납니다.
PostgreSQL 공식 저장소(PGDG)를 추가해 16을 설치합니다.

**접속 허용은 목록 방식입니다.** `pg_hba.conf` 에 필요한 대역만 추가합니다.

```
127.0.0.1/32     서버 자신
172.25.0.0/16    도커 컨테이너
192.168.0.0/16   내부 사설망 (DBeaver 등 / 서버 대역에 맞게 변경)
```

**SQL 실행 순서가 중요합니다.** 인증 → common → dtmeta 순이며, DML 실행 전에
치환자 두 개를 실제 주소로 바꿔야 합니다. 이 값이 DB에 박히고 나중에 웹 빌드 값과
일치해야 로그인이 됩니다.

| 치환자 | 바꿀 값 | 쓰이는 곳 |
|---|---|---|
| `__WEB_SERVER_URL__` | `http://서버IP:8084` | `metaweb` 앱의 `redirect_uri`, RDF 네임스페이스 |
| `__SECURITY_SERVER_URL__` | `http://서버IP:33000` | `security` 앱의 `redirect_uri` |

| 파일 | 대상 |
|---|---|
| `ddl_hubsecurity_public.sql` / `dml_hubsecurity_public_data.sql` | 인증 서버 DB |
| `ddl_dtmeta_common.sql` / `dml_dtmeta_common_data.sql` | 사용자·권한·메뉴·코드 |
| `ddl_dtmeta_dtmeta.sql` / `dml_dtmeta_dtmeta_data.sql` | 메타데이터 모델·RDF 설정 |

> DML은 `COPY` 형식이라 **`psql -f` 로만 실행됩니다.** DBeaver 같은 SQL 편집기에서는
> 실행되지 않습니다. 인증 서버 DML만 `INSERT` 형식이라 어느 도구로든 됩니다.

**필수 데이터** — 인증 DB의 `System_Admin` 롤 + `admin` 계정 + OAuth 앱 2건
(`security`, `metaweb`). 이 중 하나라도 없으면 로그인이 안 됩니다. 특히 `security`
앱이 빠지면 로그인 화면은 뜨지만 제출할 때 브라우저가 아이디/비밀번호 팝업을
띄웁니다. 두 앱의 차이는 위 "설정값 관리 방침 > OAuth 클라이언트" 를 참고합니다.

**권한이 결정되는 곳** — 로그인 인증은 `hubsecurity` DB가, 화면에 보이는 메뉴와
호출 가능한 API는 `common.tb_com_authusermap` 이 정합니다. 두 곳에 같은 `user_id` 가
있어야 하며, 권한 매핑이 없으면 로그인은 되지만 메뉴가 비어 보입니다.

## 3. Virtuoso

**하는 일** — RDF(트리플) 저장소를 컨테이너로 띄우고 앱이 쓸 계정을 만듭니다.

**계정이 두 개입니다.** 컨테이너 실행 시 지정하는 `dba` 는 관리 콘솔(Conductor)용이고,
Metadata API가 쓰는 계정은 관리 화면에서 직접 만드는 `meta_manager` 입니다.

계정 생성은 브라우저에서 합니다. `SQL/ODBC` 유형, Primary role `dba`,
그리고 SPARQL 권한 4개(`SPARQL_LOAD_SERVICE_DATA`, `SPARQL_SELECT`,
`SPARQL_SPONGE`, `SPARQL_UPDATE`)를 부여합니다.

**확인** — `meta_manager` 로 재로그인해 SPARQL 질의가 실행되면 정상입니다.

## 4. Neo4j

**하는 일** — 그래프 DB를 띄우고 플러그인 2종과 제약조건 3개를 설정합니다.

**플러그인 2종이 모두 필요합니다.**

| 플러그인 | 용도 | 설치 |
|---|---|---|
| apoc | 라벨 동적 추가 (`apoc.create.addLabels`) | `NEO4J_PLUGINS` 로 자동 |
| n10s | RDF 적재 (`n10s.rdf.import.inline` 등) | `n10s.jar` 를 수동 배치 |

> **`n10s.jar` 는 컨테이너를 만들기 전에 복사해야 합니다.** 컨테이너를 만든 뒤에는
> 플러그인 디렉터리 소유자가 컨테이너 계정(UID 7474)으로 바뀌어
> `sudo cp` 와 소유자 변경이 추가로 필요합니다.

**제약조건 3개**는 앱이 만들지 않으므로 설치 시 한 번 걸어야 합니다.
라벨과 속성 이름은 소스에 쓰인 그대로이며, `medataResource`·`medataSetId` 의
철자도 소스 기준입니다.

**`n10s.graphconfig.init()`** 도 설치 시 1회 실행합니다. `Resource.uri` 제약이
있어야 동작하므로 제약조건 생성 뒤에 합니다.

## 5. Elasticsearch & Kibana

**하는 일** — 공개 저장소 `docker-elk` 를 받아 설정을 고치고, 한글 형태소 분석기를
넣어 이미지를 다시 빌드한 뒤 기동합니다. 이 장이 가장 손이 많이 갑니다.

**고쳐야 할 파일이 3개입니다.**

| 파일 | 무엇을 |
|---|---|
| `.env` | 버전 `9.3.2`, 계정 비밀번호 3종 |
| `docker-compose.yml` | 네트워크를 `keti-dt-net` 으로 (유일한 수동 편집) |
| `elasticsearch/Dockerfile` | `analysis-nori` 플러그인 추가 → 이미지 재빌드 |

**네트워크를 바꾸는 이유** — Metadata API가 컨테이너명 `elasticsearch` 로 접속하기
때문입니다. compose가 서비스명을 네트워크 별칭으로 등록하므로, 실제 컨테이너명이
`docker-elk-elasticsearch-1` 이어도 `elasticsearch` 로 찾아집니다.

**setup은 최초 1회만** 실행합니다. 내장 계정들의 비밀번호를 `.env` 값으로 설정하는
단계이며, 완료되면 컨테이너가 스스로 종료됩니다.

**인덱스는 미리 만들어야 합니다.** Metadata API는 문서만 넣고 인덱스를 만들지
않으므로, `dtmeta` 인덱스를 설치 시 생성합니다. 이름은 앱 설정의
`elastic.index-name` 과 같아야 합니다.

> `dtmeta_vector`·`dtmeta_edges` 는 만들지 않습니다. 벡터 검색을 쓸 때 벡터 서버가
> 매핑과 함께 생성하며, 매핑 없이 미리 만들면 나중에 타입이 맞지 않습니다.

## 앱 배포 공통

**기동 순서** — 인증서버 → Admin API → Metadata API → Web. 이 순서를 지켜야
로그인이 됩니다.

**4개 앱 모두 소스에서 바로 이미지를 빌드합니다.** 서버에 JDK·Maven·Node를 따로
설치할 필요가 없습니다.

**설정값 주입 방식이 웹만 다릅니다.**

| 앱 | 방식 | 이유 |
|---|---|---|
| 인증서버 · Admin API · Metadata API | 실행 시 `--env-file` | 환경변수를 실행 중에 읽음 |
| Web | 빌드 시 `--build-arg` | Vue가 값을 빌드 시점에 코드에 넣음 |

그래서 웹은 서버 주소가 바뀌면 이미지를 다시 빌드해야 합니다.

**각 앱 폴더의 `.env.example`** 에 설정 가능한 값이 정리돼 있습니다. 값을 주지
않으면 소스의 기본값이 쓰이며, 그 기본값은 이 문서의 설치 기준과 같습니다.

**`.env` 를 고쳤으면 `docker restart` 로는 반영되지 않습니다.** `--env-file` 은
컨테이너를 만들 때 한 번만 읽습니다. `docker rm -f` 로 지우고 `docker run` 으로
다시 만들어야 하며, `docker exec <컨테이너> printenv <변수>` 로 확인합니다.

**값을 고칠 때는 `~/dt.env` 부터 고칩니다.** 앱 `.env` 는 `~/dt.env` 의 값을 그대로
옮겨 적는 구조라, `~/dt.env` 가 비어 있는 상태에서 앱 `.env` 를 다시 만들면 빈 값으로
덮어써집니다.

**주소 규칙**

| 구분 | 값 |
|---|---|
| 컨테이너끼리 | 컨테이너명 (`virtuoso`, `neo4j`, `elasticsearch`, `influxdb2`, `keti-dt-security`, `keti-dt-platformadmin-api`) |
| 컨테이너 → 호스트 PostgreSQL | `172.25.0.1` |
| 브라우저가 여는 주소 | 실제 서버 IP 또는 도메인 |

## 7. 인증 서버

**하는 일** — 로그인과 OAuth 토큰 발급을 담당하는 Node.js 앱을 띄웁니다.

**설정은 우선순위가 있습니다.**

```
환경변수  >  server_conf.json  >  server_conf.js 의 기본값
```

`--env-file` 로 넘긴 값이 가장 우선하며, 아무것도 주지 않으면 설치 기준
기본값(`hubsecurity_manager` / `172.25.0.1` / 33000)으로 동작합니다.

**이 단계에서는 로그인을 하지 않습니다.** 서버가 응답하는지(`curl` 200)와 DB 가
붙었는지만 봅니다. 실제 로그인은 웹 → 인증 서버 → 웹으로 돌아오는 흐름이라,
웹까지 올린 뒤 10장에서 확인해야 의미가 있습니다.

**JWT 서명키는 설치할 때 새로 만듭니다(7-2).** 소스에 들어 있는 키를 그대로 쓰면
누구나 같은 키로 토큰을 만들 수 있습니다. `keys/initKey.js` 로 만들어 호스트에 두고
컨테이너에 마운트하므로, 컨테이너를 다시 만들어도 유지됩니다.

| 쓰는 곳 | 내용 |
|---|---|
| 인증 서버 | `private.pem` 으로 토큰 서명, `public.pem` 으로 검증 (RS256) |
| Metadata API · Admin API | 인증 서버의 `/security/publickey` 에서 공개키를 받아 검증 |

**키를 바꾸면 API 를 재시작해야 합니다.** API 가 받아온 공개키를 **캐시**하기 때문에,
재시작하지 않으면 토큰 검증에 계속 실패하고 웹이 **로그인 화면으로 무한 반복**됩니다.
설치 순서(7 → 8 → 9)대로 하면 겪지 않지만, 운영 중에 키를 바꿀 때는 아래가 필요합니다.

```
docker restart keti-dt-metadata-api keti-dt-platformadmin-api
```

사용자도 다시 로그인해야 합니다. 옛 키로 발급된 토큰은 무효가 되며, 브라우저에 남은
토큰 때문에 계속 실패하면 사이트 데이터를 지우거나 시크릿 창에서 접속합니다.

**HSTS 는 꺼져 있어야 합니다.** `helmet()` 기본값이 `Strict-Transport-Security`
헤더를 붙이는데, http 로 서비스하면서 이 헤더를 보내면 브라우저가 이후 접속을 전부
https 로 바꿔버려 로그인 화면에 갈 수 없습니다. 포트가 아니라 **호스트 단위**로
걸리므로 웹(8084)으로 들어가도 같이 막힙니다. `ENABLE_HSTS` 를 주지 않으면 꺼집니다.

```
curl -i http://서버IP:33000/login | grep -i strict   → 아무것도 안 나와야 정상
```

한 번 켜진 상태로 접속했다면 브라우저에 캐시가 남습니다. 서버를 고쳐도 계속
https 로 가면 `chrome://net-internals/#hsts` 의 **Delete domain security policies**
에서 서버 IP 를 지웁니다.

## 9. Metadata API

**하는 일** — 메타데이터 등록·검색·RDF 변환을 담당하는 핵심 앱입니다.
저장소 5종에 모두 접속합니다.

**반드시 지정해야 하는 값이 2개입니다.** 기본값이 없어 비워 두면 기동에 실패합니다.

| 값 | 비어 있으면 |
|---|---|
| `SECURITY_SECRET_KEY` | 기동 실패(`WeakKeyException`). PAT 서명·검증용 대칭키이며 32자 이상이어야 합니다 |
| `INFLUX_TOKEN` | **기동은 되고 로그인도 되지만, 나중에 키워드 등록에서 500** 이 납니다 |

**`INFLUX_TOKEN` 이 특히 위험합니다.** 값이 틀려도 앱은 정상 기동하고 로그인까지
됩니다. 메타데이터를 등록하고 **키워드를 저장할 때** 비로소 InfluxDB 401 이 나면서
500 으로 실패합니다. 이때 앞 단계(저장·카프카 전송)는 이미 끝난 뒤라 **데이터는
저장되고 응답만 실패**하는 형태라 원인을 찾기 어렵습니다.

두 값은 설치 도중에 만들어 `~/dt.env` 에 넣는 값이라, **값 파일을 다시 만들었거나
다른 세션에서 이어서 하면 비어 있을 수 있습니다.** 9-3 에서 값을 눈으로 확인하고,
`influx bucket list` 로 토큰이 실제로 통하는지까지 보고 넘어갑니다.

`INFLUX_TOKEN` 을 잃어버렸으면 6장에서 만든 파일에 남아 있습니다.

```
grep DOCKER_INFLUXDB_INIT_ADMIN_TOKEN $DT_DIR/influxdb2/.env.influxdb2
```

**`WEB_SERVER_URL` 은 2장에서 DB에 넣은 값과 같아야 합니다.** RDF 네임스페이스
주소로 쓰이기 때문입니다.

**나머지 저장소 접속은 컨테이너명으로 고정**돼 있어 지정할 것이 없습니다.
PostgreSQL만 `DB_HOST` 로 게이트웨이 IP를 씁니다.

## 10. Metadata Web

**하는 일** — Vue 3로 만든 화면을 빌드해 nginx로 서비스합니다.

**빌드 시 넘기는 값이 로그인을 좌우합니다.**

| 값 | 맞춰야 할 대상 |
|---|---|
| `WEB_SERVER_URL` | DB `metaweb` 앱의 `redirect_uri` 와 정확히 일치 |
| `CLIENT_ID` / `CLIENT_SECRET` | DB `application` 의 **`metaweb`** 앱 |
| `SERVER_HOST` | 인증서버·API를 브라우저가 호출할 주소 |

**`security` 앱을 웹에 쓰면 안 됩니다.** 그것은 인증 서버가 자기 로그인 화면에서
쓰는 클라이언트이고 `redirect_uri` 가 인증 서버 자기 주소입니다. 웹은 `metaweb` 을
씁니다. Dockerfile 기본값이 이미 `metaweb` 이라 그대로 빌드하면 됩니다.

인증 서버는 `redirect_uri` 를 프로토콜·호스트·포트·경로까지 정확히 비교합니다.
하나라도 다르면 로그인 자체는 되지만 웹으로 돌아오지 못합니다.

**nginx 설정은 손댈 것이 없습니다.** API 프록시는 컨테이너명으로 지정돼 있어
서버가 달라져도 그대로 동작합니다.

**최종 확인** — 웹에 접속해 `meta_admin` / `rhksflwk1!` 로 로그인하고 메뉴가
보이면 설치가 끝난 것입니다. 주소창에 `http://` 를 직접 붙여 입력합니다.

| 증상 | 원인 |
|---|---|
| 인증서 경고(연결이 비공개가 아닙니다) | 브라우저가 https 로 접속. `http://` 직접 입력, 크롬 "항상 보안 연결 사용" 끄기, HSTS 캐시 삭제 |
| 아이디/비밀번호 **팝업**이 뜸 | 로그인 화면이 DB 에 없는 클라이언트로 토큰을 요청. `application` 에 `security` 앱이 있는지 확인 |
| 로그인 화면이 무한 반복됨 | JWT 서명키를 바꾼 뒤 API 를 재시작하지 않음. API 가 옛 공개키를 캐시하고 있다 |
| `redirect_uri mismatch` | DB `metaweb` 의 `redirect_uri` 와 웹 빌드값이 다름 |
| 로그인은 되는데 메뉴가 비어 있음 | `common.tb_com_authusermap` 에 그 계정의 권한 매핑이 없음 |

## 부록 A. 단계별 예상 소요 시간

빈 서버에 이 문서의 순서대로 설치할 때의 기준 시간이다.

|---|---|---|
| 0. 환경 확인 · 소스 받기 · 값 지정 | PAT 발급, sparse clone | 10분 |
| 1. Docker | 저장소 등록 · 설치 · 네트워크 생성 | 15분 |
| 2. PostgreSQL | 설치 · 접속 설정 · DB 생성 · DDL/DML 6종 | 1시간 |
| 3. Virtuoso | 컨테이너 실행 · Conductor 계정 생성 | 15분 |
| 4. Neo4j | n10s.jar 배치 · 컨테이너 실행 · 제약조건 3개 | 15분 |

| 6. InfluxDB2 | 토큰 생성 · 컨테이너 실행 | 5분 |
| **0~6 소계 (저장소)** | | **2~3시간** |
| 7. 인증 서버 | 이미지 빌드 · 설정 · 실행 · 응답 확인 | 10~15분 |

| **전체** | | **3.5~4.5시간** |

> 위 시간은 순서대로 막힘 없이 진행했을 때의 기준이다. 값을 잘못 넣었거나 확인 단계에서
> 원인을 찾다 보면 각 장마다 그만큼 더 걸린다. 특히 로그인 확인(10-4)은 웹·인증 서버·DB
> 세 곳의 주소가 모두 맞아야 통과하므로, 여기서 막히면 시간이 크게 늘어난다.
