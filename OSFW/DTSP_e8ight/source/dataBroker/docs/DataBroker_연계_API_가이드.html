00설정값 매핑 요약

현재 적재되어 있는 문서 구조는 다음과 같습니다. 이 문서의 각 필드가 API 파라미터의 어디에 대응하는지가 이번 문의의 핵심입니다.

설정값저장 위치API 상의 위치예시 값
Federated Digital Object ID attrs[name=federatedDigitalObjectId].value 및 _id.id의 마지막 세그먼트 entityId의 마지막 세그먼트, 또는 q=federatedDigitalObjectId==… KR-104111-0111
Federated Digital Twin ID attrs[name=federatedDigitalTwinId].value q 파라미터로 조회
q=federatedDigitalTwinId==KR-01-M70130-20260001		 KR-01-M70130-20260001

반드시 지켜야 할 5가지

Entity ID 조립

entityId = urn:ngsi-ld:{Type}:{FederatedDigitalObjectId} 규칙으로 생성됩니다. 콜론으로 구분된 4개 세그먼트 형식이어야 하며, 앞 3개는 데이터관리자에 등록된 데이터모델 ID와 일치해야 합니다.

Twin ID는 속성

Federated Digital Twin ID는 Entity ID에 포함되지 않습니다. 속성(Property)으로 저장되어 있으므로 q 파라미터로 조회해야 합니다.

Link 완전일치

Link 헤더의 URL은 저장된 @context 문자열과 100% 동일해야 합니다. 문자열 비교로 조회하므로 http/https, 포트, 버전이 한 글자라도 다르면 조회되지 않습니다.

Bearer 토큰 필수

모든 요청에 Authorization: Bearer {토큰} 헤더가 필요합니다. 누락 시 401 Unauthorized가 반환됩니다.

2단계 조회

목록 조회는 값을 반환하지 않고 ID 목록만 반환합니다. 실제 측정값은 그 ID로 단건 조회를 한 번 더 호출해야 합니다. (2.2절)

01공통 규격 · 인증

1.1 Base URL

  • 제공 API는 조회(GET) 6종입니다. 등록 · 수정 · 삭제 API는 제공하지 않습니다. (4장 참조)
  • 응답 Content-Type 은 application/json 입니다.

연계 구조

외부 시스템 → DataService (/ndxpro/v1/service, 54002) → DataBroker (/ndxpro/v1/broker) → MongoDB

DataService는 DataBroker의 수집처(provider) 포함 조회 API를 호출하여, 정제된 형태로 응답합니다. 따라서 모든 응답에 provider(수집처)가 포함됩니다.

1.3 Link 헤더 — Context 지정 방법

NGSI-LD 규격에 따라 @context는 HTTP Link 헤더로 전달합니다.

  • < > 안의 URI만 추출하여 사용합니다. rel, type 파라미터는 생략 가능하지만 규격상 포함을 권장합니다.
  • 추출된 URI는 문서의 @context 필드와 정확히 일치(equals) 해야 조회됩니다.

주의 — 조회 실패의 가장 흔한 원인

단건 조회(/entities/iot/{entityId}, /entities/{entityId})는 내부적으로 entityId + @context 두 조건을 AND로 조회합니다. Link 헤더를 생략하면 조회되지 않으므로 필수입니다.

목록 · 이력 조회에서는 선택이며, 생략 시 context 조건 없이 전체를 대상으로 조회합니다. 단, 응답 바디의 context 필드는 null 로 반환됩니다.

1.4 Entity ID 명명 규칙

  • 콜론(:)으로 구분된 4개 세그먼트여야 하며, 첫 세그먼트는 반드시 urn 입니다.
  • 앞 3개 세그먼트(urn:ngsi-ld:LatestPohangAtmMarModel:)는 데이터관리자(DataManager)에 등록된 데이터모델 ID와 일치해야 합니다.
  • 마지막 세그먼트에 Federated Digital Object ID를 그대로 사용합니다.

1.6 조회 파라미터에 쓰는 속성명

저장 문서에는 attrNames(축약명 → Context URI 매핑)와 attrs(실제 값)가 나뉘어 저장되지만, API 요청 · 응답에서는 항상 축약명(short name)을 사용합니다.

저장 형태API에서 사용하는 값

/entities 와 /entities/iot 의 차이

  • /entities/iot/** : IoT 수집 파이프라인으로 적재된 최신값 및 이력 대상
  • /entities/** : 범용 Entity 컬렉션 대상 (IoT 데이터도 복제 저장되므로 대부분 동일한 결과, 단 이력 조회 불가)
  • 예시로 주신 LatestPohangAtmMarModel 데이터는 /entities/iot 계열 사용을 권장합니다.

2.2 조회 흐름 — 2단계 구조

목록 조회 API는 속성값을 반환하지 않고 ID와 수집처만 반환합니다. 실제 측정값은 반환된 ID로 단건 조회를 한 번 더 호출해야 합니다.

최신값 조회

1
GET /entities/iot?type=LatestPohangAtmMarModel&q=federatedDigitalTwinId==…
→ { entities: [ { provider, entityId } ] }  ·  ID 목록만
2
GET /entities/iot/{entityId}  + Link 헤더
→ { provider, entity: { pm10, pm25, … } }  ·  전체 속성값

이력 조회

1
GET /entities/iot/history?entityId=…&timeproperty=pm10.observedAt&timerel=between&time=…&endTime=…
→ { entityHistoryList: [ { historyId, entityId, observedAt, provider } ] }  ·  이력 ID 목록만
2
GET /entities/iot/history/{historyId}?timeproperty=pm10.observedAt
→ { historyId, observedAt, provider, entity: { pm10, … } }  ·  전체 속성값

지름길

이미 Entity ID를 알고 계신 경우(= Federated Digital Object ID로 조립 가능한 경우)에는 ①단계를 건너뛰고 곧바로 ②단계 단건 조회를 호출하시면 됩니다.

04데이터 등록 (연계 송신)

DataService는 조회 전용입니다

/ndxpro/v1/service 는 등록 · 수정 · 삭제 API를 제공하지 않습니다. 데이터 송신이 필요한 경우 아래 두 경로 중 하나를 사용하며, 별도 협의가 필요합니다.

경로방식비고
Kafka 토픽 (ngsild.topic)실시간 IoT 수집현재 포항 대기·해양 데이터가 사용하는 경로. 수신 시 최신값 · 이력 · 범용 컬렉션에 동시 적재
DataBroker 직접 호출POST /ndxpro/v1/broker/entities (또는 /entities/provider)내부망 전용. 외부 공개되지 않음

참고로 DataBroker 등록 시의 페이로드 형식은 다음과 같습니다. 조회 응답의 entity 객체와 동일한 NGSI-LD 형태이며, observedAt 에 오프셋이 없는 점이 다릅니다.

등록 시 서버 처리 흐름

  1. @context URL을 실제로 HTTP GET 하여 용어 사전을 조회합니다. → 서버에서 접근 가능한 URL이어야 합니다.
  2. 각 속성명(pm10 등)을 Context에서 찾아 attrNames(e8ight:pm10)로 변환하여 저장합니다.
  3. urn:ngsi-ld:LatestPohangAtmMarModel: 로 데이터관리자(DataManager)에 등록된 데이터모델을 조회해 Type · 필수 속성 · 속성 valueType 유효성을 검증합니다.
  4. 동일 id + @context 문서가 있으면 갱신, 없으면 신규 삽입합니다.

05연계 테스트 체크리스트

  • 모든 요청에 Authorization: Bearer {토큰} 헤더를 넣었는가?
  • Base URL이 http://ndxpro-server:54002/ndxpro/v1/service 인가?
  • 목록 조회 시 type 파라미터를 넣었는가? (필수)
  • 목록 조회 응답에 값이 없는 것은 정상이며, 단건 조회를 한 번 더 호출해야 함을 반영했는가?
  • entityId가 urn:ngsi-ld:{Type}:{FederatedDigitalObjectId} 4세그먼트 형식인가?
  • 단건 조회에 Link 헤더를 포함했는가? (필수)
  • Link 헤더의 URL이 데이터의 @context 문자열과 완전히 동일한가? (http/https, 포트, 파일명, 버전)
  • Query String의 : ; = > 를 URL 인코딩했는가?
  • q · sortproperty · timeproperty에 축약 속성명(pm10)을 사용했는가? (e8ight:pm10 아님)
  • time, endTime 값이 UTC 기준 · 오프셋 없는 yyyy-MM-ddTHH:mm:ss.SSS 형식인가?
  • offset이 건수가 아닌 페이지 번호임을 반영했는가?
  • 이력 조회 시 timeproperty를 {속성명}.observedAt으로 지정했는가?
  • 이력 단건 조회 시 목록 조회와 동일한 timeproperty 를 넣었는가?
